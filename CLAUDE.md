# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

napari-maskel: the napari plugin for [maskel](https://github.com/bionetslab/maskel) (core skeletonization/feature-extraction package, installed as a normal dependency). This repo owns the interactive widget and the napari-layer visualization — nothing algorithmic lives here.

## Commands

```sh
uv sync --extra dev
uv run pytest
uvx ruff check
uvx ruff format --check
uv build
```

## Architecture

**Widget calls the core pipeline, then builds its own layers.** [napari_maskel/_napari.py](napari_maskel/_napari.py)'s `MaskAnalysisWidget._on_analyze` calls `maskel.pipeline.analyze_segmentation_mask()` to get a plain-data `AnalysisResult`, then passes the whole result into [napari_maskel/napari_layers.py](napari_maskel/napari_layers.py)'s `extract_skeleton_layers(result, base_name, config)` to build napari `LayerDataTuple`s. `AnalysisResult` itself has no `layers` field — that boundary is deliberate, keeping `maskel` napari-free. `extract_skeleton_layers` is safe to call unconditionally (an empty result just produces an empty layer list).

**Input is a Labels layer, not an Image layer**, since `maskel` now accepts multi-object instance segmentation maps (each distinct nonzero value its own object) as well as plain binary masks — the `_extraction_params` magicgui signature in `_napari.py` types `image` as `napari.layers.Labels`.

**One `AnalysisResult` can cover many objects.** `result.objects` is a list of `ObjectResult` — one per object, each already bundling its own `object_id`, crop `offset`, already-tagged `summary_features`/`branch_records`/`node_records`, and its own local-coordinate `graph`/`branch_data` (not a single graph spanning all objects). `napari_layers.py`'s branch/summary builders loop over `result.objects` directly (no id-lookup dict needed - everything about one object lives on one `ObjectResult`), offsetting each object's local coordinates into global image space, and concatenate into one combined layer per feature type (not one layer per object) so `object_id` is just another colorable/filterable property. `result.branch_records`/`node_records` (flat, already global-coordinate, already `object_id`-tagged) are read-only convenience properties over `objects`, not real fields - don't expect to construct an `AnalysisResult` by passing them directly.

**Config is shared with the CLI.** `PipelineConfig`/`ExtractionConfig`/`OutputConfig` come from `maskel.config` and are the same schema the `maskel` CLI reads/writes. The widget's **Save recipe**/**Load recipe** buttons round-trip the exact JSON `maskel run --config` consumes — don't add plugin-only config fields here; add them to `maskel.config` instead so both stay in sync.

**napari.yaml is the manifest.** [napari_maskel/napari.yaml](napari_maskel/napari.yaml)'s `version` must match `pyproject.toml`'s `[project].version` — bump both together on release.

**Spacing field: parse/validate as a pure function, wire reactively in the widget.** `maskel`'s `ExtractionConfig.spacing` lets length/radius/area features come out in physical units; napari layers always carry a `.scale` of length `ndim` (defaulting to `1.0`) but napari itself has no convenient numeric field to *edit* `.scale` (only an imprecise drag-based Transform tool, or the console) — so the widget's own **Spacing** text field is the editable surface, default-populated from the selected layer's `.scale` whenever the image selection changes. `napari_layers.py`'s `parse_spacing_input(text, ndim)` does the actual comma-separated parsing and length-vs-`ndim` validation as a standalone pure function (no Qt/napari dependency, so it's unit-testable without a real viewer); `_napari.py`'s `MaskAnalysisWidget._get_current_spacing()` calls it at read time (analyze/save-config time) rather than trusting cached state, returning `None` (isotropic pixel units) on any invalid input. This mirrors the CLI's own "warn and fall back, don't crash a whole batch" policy for a dimensionality mismatch, but surfaced as an inline `spacing_warning` label instead of a stderr print, since the GUI can validate before running rather than after.

**The widget is scrollable, and every group is a collapsible section (expanded by default).** `MaskAnalysisWidget` (a magicgui `Container`) is constructed with `scrollable=True` so it's never clipped by napari's dock panel regardless of content height — but magicgui's own `.native` deliberately returns the *unwrapped* content widget when `scrollable=True` (the scroll-area wrapper is only reachable via the separate `root_native_widget` property), and napari's `add_dock_widget` always embeds whatever `widget.native` returns. `MaskAnalysisWidget` therefore overrides `.native` to return `self.root_native_widget` instead, so the scroll wrapper actually reaches napari; `self._content_native` (captured once in `__init__` via `super().native`, before the override applies) is the real content widget with the actual child layout, used internally for assembly.

Every group (`spacing_group`, `extraction_group`, `cleanup_group`, `advanced_group`, `output_group`, `config_group`) is wrapped in a `superqt.QCollapsible` (expanded by default via `_make_collapsible`), added straight to `self._content_native.layout()` rather than through `Container.append()`. This is deliberate, not incidental: `Container.append()` inserts at a position computed from magicgui's own internal widget count, and `QCollapsible` is a raw Qt widget outside that bookkeeping — mixing the two desyncs the count and silently reorders every `self.append()` call made afterward. The only `self.append()` call left is for `self.image_widget`, since it's the first widget added (nothing to desync against yet) and `self.append()` is what makes magicgui render its "Input segmentation (labels layer)" label (via an internal `_LabeledWidget` wrapper) — a raw `.native` insert would silently drop it. `self.analyze_btn` (a `PushButton`) needs no such wrapping, so it's inserted raw, last. If you add another top-level group, insert it into `self._content_native.layout()` alongside the others, not via `self.append()`. A group's own reactive wiring (`.changed.connect`, `.enabled` toggling) is untouched by any of this — it acts on the widgets directly regardless of where they sit in the Qt tree. There's no separate "Output Directory" group any more — `select_outdir_btn` lives inside `output_group` ("Output Settings"), disabled whenever no write option is active (nothing would be saved) and paired with `output_dir_warning` (visible when a write option is active but no directory has been picked yet); both are kept in sync by `_update_output_dir_controls`.

**Dependent checkboxes are reconciled in one place, not scattered per-pair callbacks.** Several checkboxes are only meaningful while another is on (`extract_branches` gates `extract_branch_text`/`write_branch_csv`, `include_mask_radius` gates `write_radius`, `extract_summary` gates `write_summary_csv`, `extract_nodes` gates `write_node_csv`, and `fill_holes`/`closing_iterations` together gate `show_preprocessed`). `_reconcile_dependent_widgets` re-applies all of these at once — not just disabling the dependent when its parent turns off, but also forcing its `.value` back to `False`, so a checkbox can never sit checked-but-grayed-out. That matters beyond the UI: without the forced uncheck, a config saved right after turning a parent off would still round-trip an inconsistent combination like `write_radius=true, mask_radius=false` that silently writes nothing. Every relevant parent's `.changed` connects to this one method (not a bespoke callback per pair), and `_set_pipeline_config` calls it once after setting raw values from a loaded config, so a config file carrying that same inconsistency gets corrected on load too. Add a new dependent pair to the loop inside this method, not a new one-off callback.

**`CheckBox.label = "..."` after construction does not change what's rendered - use `_set_checkbox_text` instead.** Most magicgui widget types display their caption via an external `QLabel` that mirrors `.label`, wrapped around the control by `Container`'s own `_LabeledWidget` machinery - reassigning `.label` after construction updates that `QLabel` and works fine (this is how `ComboBox`, `SpinBox`, etc. get relabeled throughout `_setup_ui`). `CheckBox` is different: it has no such external `QLabel` - its caption is its own `.text`, set once at construction (from an explicit `"label"` magicgui option, or else the parameter name) and bound directly to the native Qt widget's `setText()`. Reassigning `.label` on an already-built `CheckBox` therefore updates only the Python-level attribute and is silently a no-op on screen - the checkbox keeps showing whatever text it was born with. This bug was present, undetected, for every renamed checkbox in this file until it was caught from a user screenshot showing stale text despite correct-looking source and a correctly-installed package - tests asserting `widget.label == "..."` all passed throughout, since they never touched the actually-rendered `.native.text()`. `_set_checkbox_text(widget, text)` (near `_make_collapsible`) sets both `.label` (for consistency with magicgui's own internal uses of it, e.g. unifying label widths) and `.text` (the one that matters), and is the only way any `CheckBox` in this file should be relabeled after construction. `tests/test_napari_widget.py`'s `test_checkbox_native_text_matches_intended_label` asserts `.native.text()` for every checkbox precisely to keep this from regressing silently again.

**The logo is a raster asset rendered once, not the SVG at runtime.** `napari_maskel/resources/logo.png` (bundled via `[tool.setuptools.package-data]`) is what `MaskAnalysisWidget._build_logo_label` actually loads via `QPixmap`. The source design lives elsewhere as an SVG - it was deliberately *not* shipped/rendered as SVG at runtime, since Qt's own SVG renderer (`qtpy.QtSvg.QSvgRenderer`) silently dropped the wordmark `<text>` element entirely when tested against it (a known QtSvg limitation - its SVG support is a subset of SVG Tiny 1.2 with especially weak text handling), while a proper renderer (`resvg`) reproduced it correctly. Rather than depend on a Qt submodule (`QtSvg`) that may not even be installed alongside every Qt binding napari can run on, and that demonstrably mis-renders this exact asset, the logo is rasterized once (checked into the repo as a PNG) and loaded with plain `QPixmap`, which every Qt binding supports. If the logo design ever changes, re-rasterize from the source SVG with a real renderer and verify the output before replacing the PNG - don't just drop a new SVG in and add a QtSvg code path. The label is inserted via `content_layout.insertWidget(0, ...)` *after* `self.append(self.image_widget)`, not before - see the comment there on why a raw insert done first would get silently pushed down a slot by `append()`'s own position bookkeeping.

**Any `Label` holding dynamically-generated text needs `_prepare_wrapping_label`, not just `setWordWrap(True)`.** magicgui's `Label` backend hard-codes `QSizePolicy.Fixed` on both axes at construction time (see its `_qtpy` backend source) - the label is always sized to its own unconstrained, one-line `sizeHint()` and is never shrunk by the layout, no matter what `setWordWrap()` says; `Fixed` means the layout treats that sizeHint as non-negotiable rather than a preference. `image_shape_label` and `spacing_warning` both hold text built from runtime values (image shape, a spacing-validation error) that can be longer than the dock panel is wide, so with word wrap alone, the label's fixed one-line sizeHint still silently grows the *widget's own bounding box* to fit it (the dock panel then clips the overflow) instead of ever wrapping - confirmed by feeding a 58-element shape tuple through it and watching the root widget's `sizeHint().width()` grow right along with the text length. `_prepare_wrapping_label(label)` (near `_set_checkbox_text`) fixes this properly: word wrap, plus overriding the horizontal size policy to `QSizePolicy.Ignored` so the layout disregards that sizeHint and gives the label whatever width the container actually has (verified this actually caps the root widget's width regardless of text length), plus explicit left-alignment since a box now wider than its own text needs it stated rather than left implicit. `branch_color_warning`/`output_dir_warning` hold short fixed strings and haven't hit this in practice, but any new `Label` fed from an f-string with unbounded content (a shape tuple, a user-supplied value, an error message) should go through `_prepare_wrapping_label` right after construction.

**Layer marker sizes must not be fixed absolute values.** `napari_layers.py`'s branches (a `Shapes` path layer) and its two `Points` layers (branch/end nodes, per-object summary) render fine on the small synthetic masks in tests but become imperceptible, often dotted lines/points on a full-resolution real image (e.g. a ~3500px-wide fundus photo) with a fixed data-space size, since a size tuned for tens of pixels is a rounding error at that scale. `Points` has a `canvas_size_limits` constructor arg - a min/max clamp in actual screen pixels, independent of zoom or image size - used via `_POINT_CANVAS_SIZE_LIMITS` for both point layers. `Shapes.edge_width` has no such canvas-space option in this napari version, so `_proportional_edge_width` instead scales it to the image's own largest dimension (floored at `1.0` so tiny test images still render something). If you add another marker-bearing layer, give it one of these two treatments rather than a fixed number.

**The node layer only shows branch/end nodes, not every skeleton-graph node.** `napari_layers.py`'s `_extract_node_features_layer` filters `node_records` down to `degree != 2` before building the layer (skan's graph nodes include plenty of degree-2 "pass-through" points along a straight, unbranched run — not just endpoints and junctions), and names the resulting layer `{base_name}_branch_and_end_nodes` rather than `_nodes`. This is display-only: `AnalysisResult.node_records` (and therefore the CLI's node CSV) still includes every node, degree-2 ones included — only the interactive layer is filtered, so it reads as a graph (endpoints + junctions) alongside the branches layer instead of one dot per skeleton pixel.

## Tests

`tests/test_napari_layers.py` builds real `AnalysisResult`s via `maskel.pipeline.analyze_segmentation_mask()` on small synthetic masks (including multi-object ones) and feeds them straight into `extract_skeleton_layers()` — it doesn't need napari itself running, just `maskel` installed. It also covers `parse_spacing_input()` directly. `tests/test_napari_widget.py` builds `MaskAnalysisWidget` headless (`QT_QPA_PLATFORM=offscreen`) against a `MagicMock` viewer; note that toggling a `Label`'s `.visible` (e.g. `spacing_warning`) only reports correctly if the widget's top-level window has been `.show()`n first — Qt's `isVisible()` is otherwise always `False` regardless of `setVisible(True)` calls, since it depends on the whole ancestor chain being shown.
